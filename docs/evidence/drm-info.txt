DRM device evidence — runtime/shell task group 1
================================================

Captured 2026-09-22 on the board over the CH342 console (/dev/ttyACM0,
115200 8N1), running the closure described in docs/evidence/panel-lit.md
plus the hsfreqrange fix (commit 754511d). Nothing here was produced under
QEMU: its k230 machine has no display pipeline.

How drm_info got onto the board
-------------------------------
drm_info is not in the system closure. It was cross-built on the host
(pkgsCross.riscv64.drm_info, 20 s, one derivation) and pushed over the
console with tools/push-file.py together with the two libraries it links
that the board's store lacks (libdisplay-info.so.4, libpci.so.3); libdrm,
json-c and glibc were already present at the same store paths. It ran from
/tmp with LD_LIBRARY_PATH; the board's /nix/store was not written to.

    [root@nixos:~]# LD_LIBRARY_PATH=/tmp/drm_info/lib /tmp/drm_info/drm_info > /tmp/drm-info.txt 2>&1
    [root@nixos:~]# wc -lc /tmp/drm-info.txt
      300 16480 /tmp/drm-info.txt
    [root@nixos:~]# md5sum /tmp/drm-info.txt
    fc597f606f422e981064d3ccbe8d18b5  /tmp/drm-info.txt

The 300 lines below are that file, with the shell's terminal escapes
stripped and nothing else changed.

Task 1.2 — primary plane formats
--------------------------------
Plane 1 (object 33, type Primary, the only primary plane, currently
scanning out fbcon's FB 49 at 568x1232 RGB565) advertises exactly:

  ARGB8888  AR24   present
  ARGB4444  AR12   present
  ARGB1555  AR15   present
  RGB888    RG24   present
  RGB565    RG16   present
  BGR888    BG24   present
  XRGB8888  XR24   ABSENT

Verdict: XR24 (XRGB8888), wlroots' default render format, is NOT available
on the primary plane; AR24 (ARGB8888) and RG16 (RGB565) are. The same six
formats appear on the cursor plane (35) and the two RGB overlays (37, 39);
planes 31, 41 and 43 are NV12/NV21/NV16/NV61 video planes and the last one
carries the only "rotation" property. The vendor documentation's list
(docs/display-environment-options.md section 3) was right about AR24 and
RG16 and omitted AR12/AR15/RG24/BG24; it is now superseded by this dump.

What that means for a wlroots compositor, read in wlroots-0.20.2
(the pinned nixpkgs wlroots source, meson.build:4):

  - types/output/output.c:354 initialises every output with
    .render_format = DRM_FORMAT_XRGB8888.
  - render/allocator/drm_dumb.c:224-225 gives the dumb allocator the caps
    WLR_BUFFER_CAP_DATA_PTR | WLR_BUFFER_CAP_DMABUF, so
    backend/drm/drm.c:1296-1308 drm_connector_get_primary_formats() does
    NOT return NULL (that early return needs the DMABUF cap to be absent)
    and hands back the real primary-plane format list.
  - types/output/render.c:147-190 output_pick_format() then looks the
    render format up in that list; when it is missing it logs "Output
    doesn't support format 0x34325258" and fails, and output.c:644-646
    turns that into "Failed to pick primary buffer format for output".
    There is no fallback to another format in that path.
  - backend/drm/fb.c:161-175 substitutes an OPAQUE format for an alpha one
    (opaque_substitute) at framebuffer import; it never goes the other way,
    so XRGB8888 is not rescued by ARGB8888 being present.
  - sway's `output <name> render_bit_depth 6` sets DRM_FORMAT_RGB565
    (sway/config/output.c:548-556, bit_depth_from_format at 453-462), and
    render/pixman/pixel_format.c:76 lists RGB565 among the Pixman
    renderer's formats, added with both MOD_INVALID and MOD_LINEAR at
    render/pixman/renderer.c:338-341, which intersects the plane's
    MOD_LINEAR. RGB565 is also what fbcon is scanning out today.

So: a wlroots compositor left at its default WILL fail to commit a frame on
this device, and the fix is a sway config line, not a kernel change.
Whether that prediction holds is a group 3/4 hardware claim; this file only
records the plane list and the source it was checked against. cage has no
equivalent option (cage-0.3.1 output.c sets only the mode), so an unpatched
cage is expected to fail here for this reason.

Task 1.3 — a dumb buffer scans out, with no compositor involved
---------------------------------------------------------------
modetest -s allocates its framebuffer with DRM_IOCTL_MODE_CREATE_DUMB
(libdrm tests/modetest/buffers.c bo_create) and sets the mode with it. The
default format is XR24; run against this plane it fails exactly as 1.2
predicts, and AR24 and RG16 both succeed:

    [root@nixos:~]# modetest -M canaan-drm -s 48@46:568x1232 < /dev/null
    opened device `Canaan K230 DRM driver` on driver `canaan-drm` (version 1.0.0 at 20230501)
    failed to add fb (568x1232): Invalid argument

    [root@nixos:~]# sleep 25 | modetest -M canaan-drm -s 48@46:568x1232@AR24
    opened device `Canaan K230 DRM driver` on driver `canaan-drm` (version 1.0.0 at 20230501)
    setting mode 568x1232-52.19Hz on connectors 48, crtc 46

    [root@nixos:~]# sleep 25 | modetest -M canaan-drm -s 48@46:568x1232@RG16
    opened device `Canaan K230 DRM driver` on driver `canaan-drm` (version 1.0.0 at 20230501)
    setting mode 568x1232-52.19Hz on connectors 48, crtc 46

(`sleep 25 |` gives modetest a stdin that closes after 25 s, so it holds
the mode long enough to photograph and then exits without a keypress.)

Photographs, webcam at the device's top edge looking down the panel, so
the panel's columns run left-right in the frame:

    panel-photos/09-modetest-AR24.jpg   SMPTE colour bars, ARGB8888 dumb buffer
    panel-photos/09-modetest-RG16.jpg   the same bars, RGB565 dumb buffer

Both show the seven bars (white, yellow, cyan, green, magenta, red, blue
reading from the bottom edge of the frame, i.e. from panel column 0) and
the smaller lower-third bars, replacing the ArUco registration pattern
fbcon had been showing. When modetest exited, the panel returned to
fbcon's content on its own; dmesg gained nothing during either run.

That closes the design's first risk: the driver supports dumb buffers,
they scan out, and the kernel lets a userspace process take the CRTC away
from fbcon and give it back. The second risk (no XR24) is real and is
handled above.
