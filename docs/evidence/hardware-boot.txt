Linux boots on the board (change 2, task 4.1)
==============================================
2026-09-20 19:45. First time our own Linux has run on this hardware.

THE CHAIN WORKS END TO END
---------------------------
BootROM -> our SPL at 1 MiB -> DDR -> our U-Boot at 2 MiB -> our
environment at 3 MiB -> OpenSBI -> our kernel -> our device tree.

    CPU: 0 PID: 1 Comm: swapper/0 Not tainted 6.6.36 #1-NixOS
    Hardware name: Canaan CanMV-K230 (DT)

"6.6.36 #1-NixOS" is the kernel from nix/kernel.nix, cross-compiled here
this afternoon. "(DT)" means the device tree was parsed. Userspace was
reached far enough for init to be started and then killed.

TWO DEFECTS FOUND
-----------------

1. The vendor load addresses do not fit our kernel.

   `blinux` loads:
       fw_jump_add_uboot_head.bin -> 0x3000000
       Image                      -> 0x200000
       force.dtb                  -> 0x2200000

   Our Image is 60,348,416 bytes. Loaded at 0x200000 it runs to about
   0x3B80000 -- straight over the device tree at 0x2200000 AND the OpenSBI
   payload at 0x3000000. bootm then reported:

       Wrong Image Format for bootm command
       ERROR: can't get kernel image!

   which reads like a malformed header and is not. `iminfo 0x3000000`
   confirmed the header was fine before the kernel landed on top of it:

       Legacy image found
       Image Type: RISC-V Linux Kernel Image (uncompressed)
       Verifying Checksum ... OK

   The vendor's own kernel is small enough that 0x200000..0x2200000 (32 MiB)
   holds it. Ours is not, because it is a NixOS kernel with far more built
   in. Proven by loading to non-overlapping addresses instead:

       ext4load mmc 1:1 0x200000  /Image
       ext4load mmc 1:1 0x8000000 /fw_jump_add_uboot_head.bin
       ext4load mmc 1:1 0x8400000 /force.dtb
       bootm 0x8000000 - 0x8400000

   -- which booted.

2. The DRM driver oopses when the panel in the device tree is not present.

       Oops [#1]
       epc : kfree+0x6c/0x166
        ra : drm_crtc_cleanup+0x26/0xba
       [<ffffffff807c65fc>] canaan_drm_bind+0x126/0x186
       [<ffffffff807c6720>] canaan_drm_platform_probe+0xc4/0xf0
       ...
       Kernel panic - not syncing: Attempted to kill init! exitcode=0xb

   canaan_drm_bind is calling drm_mode_config_cleanup, so the bind FAILED
   and the oops is in its teardown -- a bad pointer or double free on the
   error path, not in normal operation.

   Expected, and the card explains it: this boot used
   k230-canmv-v3.dtb, the REFERENCE board's tree, which describes an
   ST7701 480x800 panel that is not fitted here. The panel probe fails and
   the cleanup path is buggy.

   Our own k230-tdisplay.dtb, with the RM69A10, is what should be on the
   card. It was still building when this test ran.

WHAT THIS DOES AND DOES NOT PROVE
----------------------------------
Proves: stage 1, the SD layout, the boot partition contents, the selector
files, OpenSBI, our kernel and device-tree parsing all work on hardware.

Does not prove: anything about the panel, touch, the radios, or reaching a
usable shell. Userspace was entered and immediately killed by the panic.
