## Context

See proposal.md for motivation and `docs/research/omarchy-quattro-theme-compatibility.md` for pinned upstream sources. Quattro's current theme format includes data beyond its palette. Our Sway/Pixman shell and in-flight card, Settings, notification and icon work need a common appearance interface. No theme importer exists yet. Layers: **userspace and Nix**; no stage-1, kernel or device-tree changes.

## Goals / Non-Goals

**Goals:** Direct unchanged-clone use, complete data preservation, explicit surface mappings, bounded portrait rendering, reproducible defaults and recoverable live switching.

**Non-goals:** Running the Omarchy installer, sourcing foreign shell/Lua, importing desktop navigation, or adding missing hardware/surfaces just to consume their theme fields. Preserve the sibling coherent-shell motion, minimum touch targets and recovery contract.

## Decisions

1. **Read-only source plus derived generations.** Accept a theme directory or collection member. Nix fetches pinned defaults with content hashes; user clones remain ordinary checkouts. Resolve each source into a validated immutable generation in a private cache and publish it atomically. Cache identity includes actual input hashes, compatibility version, image decode policy and icon dependencies; Git HEAD alone misses local edits. Updates never perform implicit Git pulls. Retain the last working generation independently of a removed clone. Reject path escapes and executable directives as inputs, without deleting files. No plugin hooks run. A converted native theme format was rejected because it creates a fork the user must maintain.

2. **Reuse Omarchy's working mechanism.** Package pinned `omarchy-theme-color`, `omarchy-theme-set-templates`, `omarchy-theme-colors-from-alacritty`, `omarchy-theme-osc`, and relevant appearance templates with their license. Keep `omarchy-theme-set NAME`, `~/.config/omarchy/themes/NAME`, and `~/.local/state/omarchy/current/{theme,theme.name,background}` as compatible entry points. A small coordinator derived from upstream `omarchy-theme-set` handles our source selection and validated activation; a shell bridge consumes its `shell applyTheme` and `background themeTransition` payloads. Replace the desktop-specific post-theme command list with installed-client adapters. Upstream's headless mode can generate files but skips live shell/app updates, so it is not the runtime solution by itself. Pin Bash/coreutils/awk/sed/util-linux dependencies through Nix. Do not package the entire Omarchy desktop or fake every unsupported command with success stubs. A separately invented palette/template parser was rejected in favor of using their tested implementation.

   The template helper hardcodes its staging/user-template paths. Carry a minimal documented path-parameter patch so the wrapper supplies isolated staging and curated template directories without changing the user's `HOME` or writing to the clone. Default public state paths stay compatible. Limit generated template outputs to declared filenames inside staging; report unresolved placeholders before activation. The small shell-side loader parses already generated data into C/Cairo values, keeping raw keys, provenance, resolved palette, backgrounds, icon selector and compatibility report. It is an adapter, not a second palette engine. Preserve custom data and diagnose unresolved references. The coordinator must improve two upstream boundaries: `rm` followed by `mv` is not an atomic replacement for concurrent readers, and upstream tolerates failed IPC with `|| true`. Publish versioned output through an atomic pointer and require acknowledgement/rollback for our shell; serialize late app reloads against their generation. This does not require changing a theme repository.

3. **Exact override semantics.** Use the upstream helpers for aliases, derived shades, scalar/mix/gradient template operations and section replacement; generate shell defaults only if no theme `shell.toml` exists; replace each `shell.<section>.toml` section; apply machine override keys last; then evaluate consumer fallbacks. Section replacement is intentionally different from key merging. Restrict application adapters to appearance keys even if the source file can also contain commands. Legacy Alacritty palette import runs the upstream helper only against a scratch copy, never the clone. Trusted packaged helpers are distinct from executable content supplied by a theme. Every imported source is treated as theme data regardless of whether its `.git` is a directory, file or absent.

4. **One shared appearance contract.** The research inventory maps every upstream section to our surface or an explicit absent consumer. Cards consume menu and border roles; drawer uses launcher; Settings uses menu/popups/controls; notifications and image picker use their own roles. Keyboard and local app adapters share the resolved palette. Upstream bar tokens do not create a bar. Preserve gradient stops, angles, alpha composition and per-side widths using cached Cairo/Pixman artwork. Typography/spacing are scaled to handheld design constraints, with an adaptation report rather than silent pixel changes. Reuse the in-flight icon resolver with selectable theme inheritance and invalidate its cache on theme generation changes.

5. **Installed app adapters are enumerated.** Inventory Foot, htop, mpv, nano/editor, nnn/files and Help plus keyboard and Sway chrome. Document which support exact colors, terminal inheritance, restricted built-in palettes or only partial appearance control. Implement each applicable adapter and show limitations; never imply arbitrary third-party UI obeys a terminal palette. Existing sessions receive supported reloads; restart-only changes are stated without killing apps. Applicable deficits are open work, not an excuse to tick full integration.

6. **Wallpaper is a separate bounded consumer.** Enumerate upstream image/video suffixes and sniff actual format, retain all choices, lazy-generate bounded previews, decode static images once at output size, and use aspect crop by default. User fit/crop/center/solid preferences and background overlays live outside the clone. Keep per-theme source-relative asset identity across generation changes. Re-selecting the active theme can explicitly cycle, while refresh is idempotent. Videos use a muted loop with visibility/reduced-motion pause, bounded decode/output, timeout and still fallback. No claim of arbitrary codec/resolution support. A measured representative video path is an acceptance task; simply hiding all videos does not complete it. Neither wallpaper animation nor switching may worsen the existing card acceptance gates; a reduced rendering mode is visibly identified.

7. **Transactional touch selection.** Settings provides scrollable theme/background previews, tap selection, cancellable preview and apply. Prepare assets before transition; swap one generation at a scene boundary, preserving touch/focus ownership and card identity. Use existing motion rules and reduced motion. A failed consumer acknowledgement restores the previous shell generation; app reload status is reported separately. Serialize activation and retain a recovery default accessible via the existing Terminal route. No theme parsing or unbounded decoding on a drag frame.

## Risks / Trade-offs

- Upstream format drift → pin both release and inspected branch revisions; retain a fixtures manifest and explicit compatibility version; refresh fixtures deliberately.
- Desktop fonts/spacing can be unusable at 568×1232 → keep accessible hit areas and report adaptations; capture actual light and dark variants on glass.
- Large wallpapers/animation can dominate memory and CPU → measure decode RSS, idle cost and combined card workload; cap caches and pause covered media. Failed budgets remain open.
- Apps expose different theming APIs → per-app adapter coverage and truthful reload state; do not broaden into replacing apps without a follow-up decision.
- Community assets have independent licenses → review before image/site redistribution; selecting a user's checkout does not require copying it into our repository.
- Theme sections name absent lock/polkit/bar surfaces → preserve/report them without inventing functionality or compromising gesture design.

## Migration Plan

Land the planning artifacts first. Implement loader/fixtures, then shared adapters and static backgrounds in independent task groups coordinated with sibling shell owners. Add a declaratively pinned default behind an opt-in trial. Complete video-background measurement separately. Reserve the board for exact-generation captures, real touch, reboot persistence and failure recovery; retain the normal session as rollback. Enable the default only after these gates. Archive only with all implementation and physical tasks complete; a host fixture pass cannot certify the device.
