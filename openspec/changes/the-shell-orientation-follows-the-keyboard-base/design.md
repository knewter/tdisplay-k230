## Context

*Layer: Nix and userspace (a systemd service, Sway configuration, the compositor, the Rust shell client). No stage 1, kernel or device tree work.*

What exists, with its grounding:

- The shell's rotation is `k230.shell.panelTransform`, rendered into the Sway config as `output DSI-1 mode 568x1232 transform ${cfg.panelTransform} scale 1 ...` (`nix/shell.nix`, `swayConfig`). `flake.nix:296` builds the landscape profile with `"270"`.
- The panel is rotated by a patched wlroots Pixman renderer that composes the logical frame and turns it once into the scanout buffer. The patch reads `WLR_PIXMAN_OUTPUT_TURN` once, when the renderer is created (`nix/patches/wlroots-k230-output-turn.patch`), and `shell.nix` sets it to "1" only when `panelTransform != "normal"` at build time (`panelOutputTurn`). Measured: stock Pixman rotation held drawer animations at about 3.5 fps, the output-turn path at about 8.7 fps against portrait's about 10.4 (`docs/evidence/panel-landscape/rotation-performance.md`).
- Touch is mapped with `input type:touch map_to_output DSI-1` and `calibration_matrix 1 0 0 0 1 0` (identity). In landscape, logical (x, y) is panel (y, 1232 - x); injected taps and the operator's finger worked at `transform 270` (`docs/evidence/panel-landscape/README.md`). Whether that is Sway re-deriving the mapping from the output transform, or the identity matrix happening to be right for both, is not recorded for a *live* change.
- The base's chips are on hardware I2C4: XL9555 0x20, TCA8418 0x34, BQ27220 0x55, BQ25896 0x6B. LILYGO's firmware detects the base by probing them (`docs/evidence/keyboard-base/probe/README.md`). Linux binds the TCA8418 at `keypad@34`; the keyboard daemon waits for its input device and rechecks every 10 s (`nix/keyboard-base/keyboard_based.py`).
- The boot text-effects change (D9, D15) picks portrait or landscape at power-on by probing 0x6B and 0x20 on I2C4 with `dm_i2c_probe` (never 0x34), carries it in the handoff record's orientation field, and chooses the Linux player's orientation in this order: explicit option, the shell's rotation state, the record, a Linux probe for the bound TCA8418, portrait. It states the follow-up that would remove the hand-off flip is "rotation of the shell when the base attaches". This is that follow-up.
- Base-absent boots have never been observed (`display/keyboard`: UNVERIFIED), and neither has a hot attach or detach.

## Goals / Non-Goals

Goals: the rule as the user stated it; the same answer for the animation, the first frame and the running shell; no lost apps; no rotation storm from a flaky connector.

Non-goals: see the proposal.

## Decisions

**D1. Detect the base with a periodic read-only probe of I2C4, not with the TCA8418 input device.** The tempting signal is the input device named `tca8418`, since the keyboard daemon already waits for it. It cannot detect a hot attach. The TCA8418 is a static device-tree child (`keypad@34` on `i2c@91409000`); the kernel probes it once, at boot, and nothing re-probes it when a chip starts answering later, so with the base absent at boot the device never appears, and with the base present at boot the device stays registered after the base is pulled off (nothing unbinds a static I2C child when its chip stops acking, so the evdev node simply goes silent). That matches the daemon's 10 s wait loop, which exists for slow boot ordering, not for hot attach <!-- UNVERIFIED: no base-absent boot and no hot attach or detach has been done on the board, so both halves of this reading of the kernel's behaviour are from the driver model, not an observation. -->. The probe is the only signal that tracks both directions, it is the same signal stage 1 uses (D15), and LILYGO's firmware uses it.
  *The probe.* A service opens `/dev/i2c-N` for the hardware I2C4 adapter (the number is found by the adapter's name or its device-tree path, not hard-coded) and does a one-byte read, with `I2C_RDWR`, at 0x20 and 0x6B. `I2C_RDWR` is used because 0x6B (and possibly 0x34 and 0x55) are bound to kernel drivers, and `I2C_SLAVE` would fail with EBUSY on a claimed address. Pointer register 0 is the same read stage 1 does: the BQ25896's REG00 and the XL9555's input port 0, with no register written. The keypad is not probed (stage 1 does not either, because the read side effects of its pointer are not established). The base is *present* when both answer within one poll and *absent* when neither does; one answering is a partial result and changes nothing, so a half-seated connector holds the previous state rather than guessing.
  *Concurrency.* The kernel serialises adapter access, so a probe between a driver's transactions is safe. Cost: two one-byte transfers a second. <!-- UNVERIFIED: whether a probe while the base's charger or gauge driver is mid-transaction, or while the bus is wedged with the base half-seated, delays them; the first board run measures the poll's wall time and the driver's error counters. -->
  *Rejected:* (a) the `tca8418` input device alone, above. (b) A udev or netlink event on the input subsystem: same blind spot, and there is no event at all for a chip that was never bound. (c) Reading the BQ25896 or BQ27220 power-supply sysfs entries: those are the kernel drivers' cached view and do not change when the chip stops answering. (d) A GPIO or a device-tree-described detect line: the case exposes none that is known <!-- UNVERIFIED: the XL9555's input pins have not been mapped for a presence line; the schematic was not consulted here -->. (e) Probing from the compositor: a blocking bus call has no place in the render loop.

**D2. Debounce: slow to rotate, slower to un-rotate, and never mid-gesture.** The poll period is 1 s. Attach is accepted after 3 consecutive "present" polls; detach after 5 consecutive "absent" polls (a base pulled away is less likely to bounce back than a seating connector is to chatter, and falsely un-rotating under a typing person is the worse error). A partial result (exactly one chip answers) resets neither count. After any rotation, no further rotation for 10 s. A rotation is deferred while a touch contact is down or an on-screen-keyboard animation is running, and applied at the next idle tick; the deferral is capped at 2 s, after which the rotation is applied anyway so it cannot be starved. Constants are options, so the board run can tune them. These numbers are a starting point <!-- UNVERIFIED: the connector's real bounce on attach and detach is unobserved; the physical task records it and the constants are revised from it. -->.

**D3. One decision, taken before the compositor, then followed at run time.** An orientation service, `k230-orientation`, runs as a `oneshot` ordered before `shell.service`'s compositor and writes `/run/k230-shell/orientation` (`portrait` or `landscape`, atomically replaced, one line) from a single initial probe with no hysteresis (nothing is displayed yet, so there is nothing to flicker). The compositor's config is generated at start from that file, so the *first frame* is already in the right orientation. The service then stays running as the poller of D1/D2; on an accepted change it rewrites the file, then runs `swaymsg output DSI-1 transform <normal|270>`. A failed probe at the initial decision (no adapter, any error) means portrait, the same fallback as stage 1. If the stage 1 record's orientation is available (boot text-effects task 5.2) and disagrees with the probe, the probe wins and the disagreement is logged, which is the existing player behaviour.
  *Option shape.* `k230.shell.panelTransform` gains a third value, `"auto"`; the existing `"normal"` and `"270"` keep their meaning and remain the default (`"normal"`), so every existing profile and its evidence is unchanged. A companion option `k230.shell.keyboardBaseTransform` (default `"270"`) names the landscape transform used when the base is present. Rejected: a separate boolean, because it would make `panelTransform = "normal"` plus `follow = true` an easy contradiction to write.

**D4. Everything that reads `panelTransform` at build time must read the file at run time under `"auto"`.** From the grep of `nix/` and `flake.nix`: `shell.nix` (`panelOutputTurn`, the Sway config, the on-screen keyboard height default of 400 vs 240, the `initialSplash` assertion that requires "normal"), `textfx-service.nix` (`orientationArg`), `touch-trackpad-service.nix` (`--panel-transform`, which the HDMI relay uses to map the panel's orientation), `nix/touch-trackpad/src/orient.rs` (`from_panel_transform`). Each gets a run-time source: the file for the player and the relay (they read it at start and when notified), and for the keyboard-height default a compositor-reported logical size rather than the option. `initialSplash` is incompatible with `"auto"` and the assertion says so; the boot animation is the hand-off surface under this change. The player's order becomes: explicit option, `/run/k230-shell/orientation`, the stage 1 record, portrait (the Linux-side TCA8418 probe step is replaced by D1's probe, which is the service's own).

**D5. A live transform change must be shown to work, and the output-turn renderer is the risk.** `WLR_PIXMAN_OUTPUT_TURN` is read when the renderer is created, so a compositor started portrait (turn off) cannot rotate cheaply later. Options: (1) start the compositor with the turn renderer on whenever `panelTransform = "auto"`, and use it in both orientations; this costs nothing in landscape, and in portrait it is only acceptable if it does not slow the portrait path <!-- UNVERIFIED: the patch's behaviour on a `transform normal` output with the turn renderer enabled, and its frame cost, have not been measured; the output-turn bench would be run in portrait first. -->; (2) fall back to stock Pixman rotation in landscape (about 3.5 fps on drawer animation, measured, rejected as a regression from what the landscape profile ships); (3) restart the compositor on a change (kills every app, rejected). Option 1 is the plan; if the portrait measurement fails the budget the design is revisited, not silently shipped. Separately, the card shell sizes its policy configuration from the output (`cs_default_config(output->width, output->height)` in `ensure_ui` and again when it lays out) and caches logical-output decisions from `output->transform` (`cache_output_logical`, `motion_scene_at_render`); whether a live transform change re-runs those is unobserved <!-- UNVERIFIED: read from adapter.c only; the board test is the injected-event task. -->, and the task list makes the adapter's re-entry an explicit item with a QEMU-reachable proof.

**D6. What happens to running apps.** Sway handles `output transform` as an output change: it recomputes the logical output (swapping width and height), re-arranges the layout, and sends each affected surface a new configure, which is the same path as a monitor's mode change. The expectations per class, all <!-- UNVERIFIED: no live rotation has been done on this shell -->:
  - *wlr-layer-shell surfaces (the Rust shell client's wallpaper, Home, Drawer, shade, power sheet, on-screen keyboard)* are anchored to all edges and receive the new output size as a configure. The client accepts a whole-output configure at 1232x568 or 568x1232 (`configure_acceptable` / `is_whole_output_size`, `nix/rust-shell-client/src/lib.rs`), and `update_output` already re-offers refused configures "when the panel rotates" (`main.rs`). Its `transform_changed` is a no-op, which is correct because the client does not set a buffer transform. What is not established is that every surface (Drawer search state, the keyboard at 400 vs 240 px, Settings) re-lays out from the new configure rather than from a size it cached; the host task renders each surface through a portrait-to-landscape-to-portrait configure sequence and compares against the existing `panel-landscape` and portrait renders, so a stale-size bug fails on the host.
  - *xdg toplevels (Foot, the editor, GTK and Qt apps)* are tiled or fullscreen by the shell's Sway policy, so they get a configure with the new size and resize like any window; Foot re-flows its cell grid and sends SIGWINCH to its child. Apps that ignore resize are clipped or letterboxed by Sway, not killed. Scroll position, text selection and in-progress input live in the app and are not preserved by the shell; the spec only requires that the app is still running and its window fills the new output.
  - *The card overview and the Home screen's pages* are shell state, not app state; they are kept, and re-laid out.
  - *Video playback* may restart its sink on a resize; it is an app behaviour and is checked, not promised.
  Rejected: closing or restarting apps on rotation (loses user state for no benefit); pinning apps to their original orientation (an app sized 568x1232 inside a 1232x568 output is unusable).

**D7. Touch follows the output, so the matrix is left alone.** Because the touch device is mapped to DSI-1 with the identity calibration, rotation is the compositor's job: the orientation service never writes a calibration matrix for the panel. The evidence that this is right is the existing landscape result (same identity matrix, finger worked at `transform 270`). What a live change adds is that Sway must re-derive the mapping on the transform change; the task is an injected tap at the four corners of the glass in each orientation, before and after a rotation, using `tools/inject-tap.sh` converted by the recorded mapping (logical (x, y) is panel (y, 1232 - x) in landscape). The HDMI path is untouched: the relay and its matrix switching only act while `HDMI-A-1` is active, and the orientation service skips the touch step entirely then; it still tracks and applies the panel's transform so the panel is right when HDMI is unplugged. The relay's `--panel-transform` argument is replaced by the file under D4.

**D8. Not every transition is a rotation.** If HDMI is the active output, the DSI-1 transform is still kept current but nothing visible changes. If the shell has not started (a rotation event before `swaymsg` works), the service writes the file and the start-up config picks it up. If `swaymsg` fails, the service logs once, keeps the file as the intended state, and retries on the next tick rather than looping.

**D9. Consistency with the boot animation.** The animation's orientation is the hand-off promise: stage 1 decides with `dm_i2c_probe` of 0x6B and 0x20; Linux decides with `i2c` reads of the same two addresses. Under the same physical state they agree; they can disagree only if the connector moved between the two probes, in which case the existing D15 rule applies (the player logs it and replays from frame 0 in the Linux orientation) and the shell's first frame follows Linux. This change does not alter the record format or stage 1.

## Risks / Trade-offs

- Wrong detach rotates the UI under a typing person. Mitigation: the 5-poll detach, the partial-result rule, the dwell, and the deferred-while-touching rule.
- A wedged I2C bus with the base half-seated could block the poller. Mitigation: each probe has a bounded wait and runs in the service, never in the compositor; a probe that does not return within 500 ms counts as "no answer from both" for that poll only. <!-- UNVERIFIED: the wedge has not been provoked; the physical task observes a slow seat. -->
- Portrait with the turn renderer enabled might be slower than today's portrait. Mitigation: D5 gates adoption on a measurement.
- Foot and other apps repaint the whole screen on resize at a time the CPU is saturated by the rotation itself; the physical task records one rotation with a terminal open and a video playing.

## Migration

None for existing users: the default is `"normal"` and `"270"` is unchanged. The `"auto"` value is opt-in per profile until the physical evidence exists; the evidence decides whether the keyboard-case profile switches to it.

## Open Questions

1. Should the keyboard-case profile move to `"auto"` once proved, making `"270"` only a pin? (The user's sentence suggests yes.)
2. Is a 3 s attach and 5 s detach latency acceptable, or should the user be able to force a rotation from Settings?
3. Does the user want a lock that holds the current orientation until released?
