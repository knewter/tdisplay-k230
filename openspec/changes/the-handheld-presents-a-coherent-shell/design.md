## Goals / Non-Goals

**Goals:** A full gesture interface with one compositor-owned motion scene, live-card Overview followed by pinned Home and the drawer from below, shade from above, truthful Settings, private notifications, predictable Back/keyboard behavior, and tested physical recovery. Desktop-entry icons accompany names and never leak private app identity.

**Non-Goals:** Permanent navigation rail/footer in the final session; synthetic universal Back into arbitrary apps; a second competing Home destination; a new compositor or GPU chosen without measured reason; haptic work on the current board; battery/telephony/account services; changing the sibling's bounded live-card source/close lifecycle.

## Decisions

1. **Overview and pinned Home have separate roles.** The accepted `runtime/home-screen` topology supersedes the original deck-as-Home plan: a bottom upward app gesture reaches the live-card Overview, a new upward gesture from Overview’s bottom navigation area reaches pinned Home without closing apps, and a new upward gesture from Home reaches All apps. Swiping a card itself upward retains its close action. Empty Overview offers a stable route to Home and Terminal in All apps. The old bar remains a separately selectable rollback session; normal composition has no permanent rail/footer.

2. **Home opens installed apps.** The drawer rises from Home’s bottom edge, tracks the finger and settles on release; cancellation restores the previous scene without launching. From an app, a pure upward bottom gesture reaches Overview, while a qualified two-axis gesture may select an existing neighbor. Apps launch only through their deliberate targets. Desktop-entry icons and readable names retain bounded caching, fallback and privacy rules. Help in All apps opens guidance and an optional deliberately selected large-labeled Navigation buttons view; changing route dismisses the aid. Search is the already-landed drawer capability, not deferred by this archive.

3. **Top-edge shade owns notifications and Settings.** A downward pull from the top reveals a nonmodal shade over the current scene. It contains a notification list and Settings entry; ordinary previews enter near its top edge and retreat into history/count without shifting or focusing the app. Settings opens within the shade's spatial path, not a separate System button. A side swipe on a history item reveals Dismiss and commits only after a clear threshold; critical ongoing events remain. The existing privacy/priority/event broker policy stays intact. A later `org.freedesktop.Notifications` adapter is optional after explicit shell/system and integrated-app sources work.

4. **Back is contextual shell navigation (side-edge mechanism moved to the authorized successor).** An inward swipe from a qualified side edge closes the top shell context: long-press sheet, Settings, shade, drawer, then keyboard when keyboard focus owns the touch. A Back gesture in app content is not translated to an arbitrary Escape/Alt-Left keypress. Apps differ in navigation semantics; app content keeps its own scroll/selection/edge handling outside a verified shell edge. Bottom Home remains the shell escape from an app or overlay. Help and accessibility aid explain routes, but permanent Back/Home buttons are rejected for the final interface.

5. **One touch owner wins at down and can cancel cleanly (general arbiter moved to the authorized successor).** The compositor arbitrates bottom Home/drawer, top shade, side contextual Back, keyboard insets, live-card drag, active overlay and app content using measured hit regions and direction/distance gates. The keyboard's lower region wins against bottom navigation there; a visible affordance or tested outer region still reaches Home, and keyboard dismissal never types into the app. A second contact, focus loss, view unmap, motion reversal, or premature release cancels from the current visual position, without turning the stream into a tap. The exact regions are provisional until real-finger trials; failed conflict gates keep the existing rollback session active. A gesture cue is shown at rest/first use, then can quiet down; it never needs a full-width button dock.

6. **Use the selected Sway scene owner for cross-surface motion.** The sibling card implementation owns live source eligibility, direct drag, expand, graceful-close request/refusal and seat focus lifecycle. This successor adds a single interruptible spatial state above those events. Sway owns the live scene trees, touch arbitration, z-order and focus; launcher/shade clients submit intent and geometry, without trying to animate another app's pixels. App→deck maps one live rectangle into its card slot; deck→drawer rises from the bottom, shade→Settings descends from the top; card→app expands from its visible slot; throw tracks up and disappears only on observed exit. Current transform, target, velocity, source identity, pointer/focus owner and z-order are kept for reverse/retarget. A new gesture starts from the displayed state, not a reset keyframe. Client-only fake thumbnails, a second DRM owner, and a default new compositor are rejected because they cannot meet the live/focus contract without separate proof.

7. **Motion references and deferred measurement.** Quantitative trace implementation and the board budget run remain in the existing side-edge/motion successor, not an archive gate for this accepted shell. No budget number or pass is claimed here. Palm/Android references supply action/direction, not numeric timing. Finger tracking occurs for every accepted movement, with one-to-one displacement of the manipulated panel edge or grabbed live-card point until its travel bound. The recognition/release threshold is independent of visual travel: crossing it while still touching does not finish a transition. A held finger stops movement; reversal immediately follows the same position mapping. Inertia and easing apply only after release or cancellation. A bounded velocity estimate settles a card to at most one adjacent slot per release initially; lists coast inside content and stop on new touch without activating a row. Reduced motion shortens settling but retains drag, scene identity, destination and feedback. Scene damage/output scheduling owns animation ticks; frame-done and output-presented are logged separately. The approximately 52.19 Hz advertised mode implies about 19.2 ms nominal intervals, not measured scanout. Declare p95/p99 input-to-present, frame interval, CPU/RSS and blank-frame budgets before board tuning; proposed review target is no unexplained blank frames and p95 input-to-present within two observed output intervals during two live apps. If Pixman misses, trim decoration and unnecessary damage first; do not replace live tracking with a static capture. A renderer/compositor change needs a separate cost decision.

8. **Visual grammar follows the active appearance.** The former fixed teal palette is superseded by the active Omarchy generation's authored section brushes, foreground, readable secondary foreground and accent. Gradient stops, direction and alpha remain intact; no decorative wash or alternate brand palette masks them. Type has clear title/body/meta roles, an 8-pixel rhythm and 24-pixel inset. Keep established hit geometry and at least 56-pixel controls. Expose themed desktop-entry artwork on Home rather than boxing each icon; give unresolved icons a deliberate neutral glyph container. The dock is one quiet tray, not nested trays. Ordinary control/notification rows use low-emphasis themed surfaces without routine border outlines. Focus, pressed selection, destructive confirmation and drag/drop retain deliberate cues. Theme carousel cards have rounded clips and a focused/active cue rather than outlines around every preview. Existing borderless clock/weather widgets remain borderless. The shell has no permanent Back/Home footer.

   **Bounded 2026-10-01 polish:** `docs/evidence/mainline-display/physical-2026-10-01/final-runtime-home.jpg` shows nested icon/dock plates on the actual panel; `docs/evidence/theme-picker/row-repaint/preflight.png` shows rectangular theme preview outlines. These observations ground the problem, not the proposed result. Change userspace paint/style paths only. Preserve compositor overview/card movement and the coordinator's renderer damage/caching work. Show matched native-resolution host renders for Home, drawer, Settings, shade and theme picker using real pinned dark/light theme appearances and wallpapers. A overview/card review image must explicitly identify its existing compositor capture; this pass cannot claim to have rendered live cards in the Rust client. The user accepts the installed result and waives a further real-glass dark/light recording; unrecorded per-surface contrast cases remain UNVERIFIED. Rejected: an invented brand palette, opacity masks flattening authored brushes, nested icon rectangles, a renderer rewrite and permanent navigation buttons.
9. **The final shell UI client targets Rust; the compositor boundary stays put.** Sway/wlroots remains responsible for live app/card pixels, touch arbitration at app/deck boundaries, z-order and focus. A Rust client owns drawer/shade/Settings surfaces, their finger state and route requests over the existing bounded session IPC. Existing C launcher source is a development reference and rollback, not the final client. Current Settings and notification helpers are separate Python services; a Rust UI does not imply they have been rewritten. The pinned `nix/rust-shell-probe/` has now cross-built as a small layer-shell client using `wl_shm` software buffers and the existing overlay namespace; its historical comparative 568×1232 map/touch/resource/cadence trial is waived by the user. The production Rust shell has separate exact runtime/native-board identity and accepted interaction; no Rust/C/Qt comparative result is claimed. Host build and QEMU prove different things from a real touch/panel run. If Rust runtime or cost fails, retain the C reference and Qt results as evidence; do not assert a toolkit choice from source availability alone.

10. **Build one opt-in Rust UI client from the proven protocol boundary.** Keep `nix/rust-shell-probe/` frozen as a reproducible feasibility artifact; create a separately pinned `nix/rust-shell-client/` and `.#handheld-shell-rust` for the actual drawer, shade and Settings. Reuse the probe's Wayland/layer-shell/SHM route semantics and released-buffer discipline, not its diagnostic drawing. Render software surfaces with Cairo plus Pango text bindings against the Cairo/Pango libraries already used by the C rollback client; this supports readable shaping, clipping, gradients and borders without a GTK widget stack. Evaluate the exact Rust binding dependency graph and cross-build before adoption; the production package is selected in the accepted daily mainline system with retained rollback; numerical board measurement is deferred. Use GIO's desktop-entry semantics for installed names and launch, resolve icons through the selected freedesktop theme with bounded decode/cache and neutral private fallbacks, and keep all blocking catalog/decode/service work outside the Wayland dispatch path. The Rust process consumes the existing Settings JSON command, notification history socket, appearance-generation receiver contract and theme catalog command; it does not replace those services. Theme chooser preview/activation and all themed surface roles retain their own `the-shell-loads-omarchy-themes` acceptance gates. The compositor, not the Rust client, continues to move live app pixels, and no probe-only rectangle counts as the final drawer.

11. **A bottom gesture keeps both axes until release and switches directly between apps.** The compositor retains the same contact from app entry through lateral selection; moving up then sideways does not require an up/down pair or a new gesture owner. Vertical motion controls the app-to-card transform and horizontal motion translates the held scene point one-to-one, exposing the neighboring card in the drag direction. There is no axis lock that discards the other coordinate after recognition, no automatic progression while held, and no reset of geometry when the path bends. A pure upward release past the existing Home threshold settles into the deck. A qualified lateral release settles the visibly selected neighbor directly in a full or near-full app carousel; it does not first complete entry into the overview, recenter a card, or start a second expansion animation. A horizontal start anywhere along the bottom edge band uses only a slight zoom proportional to actual upward travel (none if the swipe stays purely horizontal), while a curved upward-then-sideways gesture retains its achieved vertical geometry. A short/reversed release returns to the originating app. At most one neighbor is committed per release initially; the corresponding horizontal travel bound is visible, with no wrap-around. A new touch stops settlement and retargets from the displayed geometry. (The "bottom-center band" qualifier here is superseded by decision 12 below: recognition no longer depends on start position.)

    Both routes use the same deck ordering: dragging content right exposes its left neighbor, and left exposes its right neighbor. Focus-only switching does not reorder that sequence, so reversing the quick switch returns predictably. The compositor snapshots stable app IDs for the gesture and reconciles inserts/removals without substituting an unrelated target; a vanished/non-focusable target restores the source or a valid deck. Private/unavailable entries retain the sibling's neutral preview rules and may be activated only through its existing focus policy. With one app or no neighbor in a direction, keep a bounded edge response and restore the source; do not start another app or wrap around. Only the settled target receives focus and is raised visibly.

    Initial quick-switch recognition is confined to the central half of the existing bottom edge band, excluding keyboard-owned pixels and active shell overlays. That region is a provisional host geometry, not a physical usability claim. Bottom-corner and side Back ownership stay separate; ordinary app scrolling/selection outside the region stays with the app. The drawer gesture from Home remains a separate route. Thresholds select the release destination but never multiply movement. Release settling for both horizontal switching and vertical Home starts at the displayed position and measured, bounded swipe velocity, then smoothly decelerates or springs to the destination without an initial position or derivative jump or an intermediate forced overview. No timer advances the scene while the contact is held. Second contact or cancellation drains the owned stream without an app tap or throw-close. Reduced motion preserves the same geometry and destinations with shorter settling. This central-band gate is superseded below.

    The user's request on 2026-09-24 adds these two-axis and quick-switch routes to the installed vertical-only entry. `nix/card-shell-policy/card-shell-policy.c:cs_entry_motion` currently derives only vertical progress; the installed one-axis correction is recorded in `docs/evidence/coherent-shell/direct-drag/installed.md`. [Google's Android gesture guide](https://support.google.com/android/answer/9079644?hl=en) documents bottom-edge switching, and [Google's gesture navigation codelab](https://codelabs.developers.google.com/codelabs/gesture-navigation) describes conflicts with app controls near that region. They inform the interaction, not K230 proof or an exact two-axis trajectory. Requiring a lift between entry and lateral selection was rejected because it breaks direct manipulation; changing the whole deck to focus-reordered history was rejected because left/right reversal would become unpredictable.

12. **The central-band quick-switch gate is dropped; distance/velocity alone decide a lateral switch.** A same-day real-finger board report on the just-landed two-axis entry found the central-band gate itself broke the primary case it was meant to serve: an 80%+ horizontal swipe starting near either side of the bottom edge still snapped back to the source app, because a pure lateral swipe outside the central half additionally required simultaneous upward travel past `entry_distance`, which an intentionally horizontal swipe does not produce. Recognition now depends only on measured lateral displacement (about 30% of the panel width, matching the target 25-35% range for a deliberate page-turn) or release velocity (about 0.4 px/ms in the swipe direction), independent of where along the qualified bottom edge band the touch started; the vertical-progress requirement is dropped for a pure lateral switch, though up-then-sideways still works identically. Release velocity is now a recency-biased estimate that walks back through recent samples only as far as needed for a stable interval (minimum ~6ms span, capped at ~120ms to bridge a sparse ~100ms event cadence), instead of a single last-interval delta gated by a fixed 80ms freshness window; the old gate zeroed momentum whenever dispatch lagged, the event cadence was sparse, or the finger's last recorded sample preceded a slightly later release. A flick back toward the start still cancels the switch. Keyboard-owned pixels, active shell overlays and the existing bottom `edge_band` remain the only positional gates. Measured touch cadence (`docs/evidence/touch-reports.md`, `docs/evidence/touch-evtest.txt`) shows real reports arriving roughly every 8ms during continuous motion, informing both the window bound and its minimum span. See `docs/evidence/card-shell/app-switch-swipe/` and `nix/card-shell-policy/card-shell-policy.c:cs_entry_up_at`.

## Risks / Trade-offs

- [Bottom or side gesture conflicts with wvkbd or app content] → test physical ownership and cancellation; retain rollback bar session until the final route passes, then remove it from normal composition.
- [Gesture discovery is weak without permanent buttons] → show small drawer/shade/Home cues in context and offer a deliberately opened Help/accessibility aid; test first-use success on glass.
- [Live motion misses Pixman frame cost] → keep opt-in scene and measured rollback; reduce decorative work before any separate renderer decision.
- [Private card icon or title leaks identity] → replace both before scene presentation, then test unmap/reuse and cache behavior.
- [Shade changes app focus or leaks sensitive text] → preserve focus, redact unsolicited previews, and verify active keyboard and card drags.
- [No proven haptic actuator] → all accepted touch states have complete visual feedback; vibration is outside this change.
- [Rust target or software rendering exceeds the K230 resource budget] → pin dependencies and cross-build a minimal `wl_shm` probe first, then measure exact board mapping/touch/CPU/RSS against C and Qt; do not promote the probe to the normal session without the existing physical acceptance gates.

The opt-in coherent system also needs a bootable image identity, distinct from
the normal rollback image. Reuse `mkBoardImage` for a `sdImage-coherent` output
while retaining `sdImage` on the normal system. Its boot partition carries the
coherent system's exact `init=` closure selection, kernel, initrd and device
tree. A running `switch-to-configuration test` is only a reversible preview:
the external bootloader hook is a no-op and U-Boot imports the fixed
`/boot/bootargs.txt`, so neither a profile update nor
`switch-to-configuration boot` alone selects this session after restart.
For later persistent selection, compare the matching image's complete boot
file hashes with the installed files, preserve the previous selection and
recovery image, and update only the files that differ under a reserved board
procedure. A full image flash remains the fallback, not a prerequisite for
userspace-only changes. An ordinary reboot and exact running-system and
service identity are separate physical proof gates.
