## Context

The installed system has a 568×1232 portrait RM69A10 panel and GT9895 touch; physical shell evidence is in `docs/evidence/shell-features/` and `docs/evidence/shell-real-touch-*`. The shell is Sway/Pixman with Foot, a persistent top bar, wvkbd, and a native desktop-entry launcher. The launcher gesture/metadata overview, catalog curation, recovery wording, card-composition probe, and live-card product are separately owned OpenSpec changes. `docs/research/handheld-ux/interaction-contract.md` sets the 56-pixel target, contrast, focus, and visible fallback baseline. Its proposed frames and this change are not shipped behavior.

The original visual proposal is [the SVG contact sheet](../../../docs/design/handheld-shell/surfaces.svg) with [transition map](../../../docs/design/handheld-shell/transitions.md). These are 568×1232 schematic surfaces at half scale, annotated as proposed. They prove layout intent only. Historical reference comes from the [Palm Pre User Guide](https://support.bell.ca/_web/guides/User-Guides/Mobile/PalmOne/Palm-EN/palm_pre_userguide_en%28en%29.pdf), especially card view and Quick Launch around pages 23–26 and notifications/dashboard later in the guide, and the archived [HP developer description of banner and dashboard notifications](https://www.banneret.nl/webos/documentation/all/dev-guide/mojo/dashboards-notifications.html). We borrow continuity, direct touch, and deferred notification handling; we use neither Palm assets nor its specific gesture strip, nor television webOS. These sources describe historical design, never K230 capability. The system and board evidence cited above grounds the current hardware boundary.

## Goals / Non-Goals

**Goals:** A common shell grammar, explicit route and focus ownership, settings backed by actual adapters, and notifications that preserve context and privacy. Host fixtures can prove state policy before physical review.

**Non-Goals:** A new compositor, a duplicate card implementation, invented device sensors, battery UI, an OS lock screen, or making mockup pixels a shipped promise.

## Decisions

1. **Give the shell one spatial grammar with explicit navigation.** The target experience is app pixels shrinking into the same card seen in Windows, with adjacent cards maintaining position and an action dock shared by Windows and Apps. A compact nonmodal preview gives way to a deferred dashboard in System. These are the useful Palm phone webOS qualities; their pixels and gesture strip are not copied. The persistent top rail labels are exactly Apps, Windows, Keyboard, System. System opens a hub with separate Settings and Notifications entries; a pending count appears on System, and a preview itself opens its event. Each overlay has separate Back and Home footer actions. Final Home means the idempotent Apps landing; Terminal recovery is named Terminal in Apps and the recovery route. The installed Home-to-Terminal behavior remains during opt-in rollout until Apps/Terminal fallback and real-glass recovery pass together, then the modified `runtime/shell` requirement takes effect. The top rail stays through staged delivery because it is the installed, physically used entry path while the app-to-card route remains unverified. A future bottom dock is not selected now: the keyboard occupies that region and physical reach/occlusion evidence is absent. The final visual target is the integrated deck and dashboard, not merely the current bar with new colors.

2. **Use a quiet dark material, not blur.** Canvas `#101822`, surface `#1B2934`, raised `#263946`, text `#F4F7F8`, secondary `#C8D7DD`, accent `#78D7CB`, warning `#FFC27A`, error `#FFB2A8`, 2-pixel focus stroke. Typography is Nix-packaged sans/Pango roles 42/32/22/18 pixels for title/card/body/meta. Space in 8-pixel steps; 24-pixel page inset; at least 56-pixel controls. Current Sway output is 568×1232 at scale 1, so those logical target pixels currently map 1:1 to panel pixels; any later scale must preserve physical target dimensions. Keep overlaid text on opaque fills and source-color contrast at least 4.5:1. Reject wallpaper blur, translucent live glass, and gradients under body text because CPU/Pixman cost and optical contrast are unproved. Confirm actual glass contrast and target reach with camera and real finger evidence.

3. **Treat cards as another shell destination, with a capability gate.** Windows opens the existing metadata route until the card product has physical live-surface proof. Once enabled, the app-to-deck transition and drag/expand/throw lifecycle belong to `the-shell-manages-apps-as-cards`, consuming `the-shell-has-a-card-composition-plan`. This design owns only frame, labels, selection/recovery, privacy placeholder, and cross-surface routing. A snapshot or metadata row must never be labeled live. Reject parallel screencopy thumbnails and a second DRM owner because they duplicate or bypass the existing contract.

4. **Use desktop entries as the sole app catalog source.** Apps groups readable action labels and preserves built-ins, Help, paging, failure copy, and keyboard viewport. `the-launcher-explains-app-actions` owns catalog curation. Search is deferred until keyboard focus, matching, and cost can be proven; the mockup shows no nonfunctional search box.

5. **Settings use explicit capability adapters.** A userspace settings view receives read state, write availability, and confirmed value from narrow system interfaces. Initial rows: network status/open existing Wi-Fi flow; display brightness only if the installed backlight interface can be read and written; keyboard/reduced-motion preferences; restart/power actions through the existing authorized system helper. Unavailable rows explain why and offer Back, never optimistic success. Nix supplies defaults for fresh homes. No battery row or battery-only boot state. Reject a broad privileged settings daemon or UI toggles without a real control path.

6. **Notifications are event records, not arbitrary popups.** A userspace broker accepts bounded source/title/body/action metadata, assigns monotonic IDs and ordinary/important/critical priority, deduplicates repeated events, and limits history (proposed 50 entries/7 days; adjust only from measured use). Preview is a non-focus-taking strip below the rail, at most one at a time; pending events queue into history and count on System. Ordinary preview expires after 5 seconds; important after 8; critical remains until acknowledged or condition clears. Only trusted system producers may assert critical. Unknown producers are ordinary and body-redacted. The first integration covers shell/system events and apps deliberately wired to the broker. A later `org.freedesktop.Notifications` adapter may accept standard desktop events while respecting the same privacy/priority policy; it is not needed for the first proof and no capture of every desktop event is claimed. History shows full detail after deliberate open; transient previews show neutral summary for sensitive events. Actions are typed open/retry/acknowledge routes, validated at invocation; dismissal is separate. Reject modal ordinary alerts, unbounded history, and executing sender-provided commands.

7. **Priority and focus are deterministic.** Active touch drag, keyboard typing, confirmation, and app focus are never stolen by ordinary/important previews. If a preview would cover the focused input, place it below the rail only if clear or suppress it to history and show a count. Critical messages may interrupt visually but still preserve the visible Back/Home/recovery route. In a conflict, card drag owns its pointer until release/cancel; page swipes start only in the launcher content region; vertical edge/system gestures remain disabled until independently proven. Keyboard activation reserves its measured lower inset and recomputes overlay actions above it. Back closes history/settings/Apps top-first, then returns to prior app or deck; Home is the explicit escape. Physical edge and focus behavior remain UNVERIFIED.

8. **Animate meaning only.** Proposed transition is 120–180 ms, release-to-final-submit at most 200 ms CPU-side, with a zero-duration reduced-motion variant. Live finger tracking is not replaced by release-only motion. If a frame budget or memory gate fails, remove decoration while preserving destinations and input feedback. The already measured launcher transitions do not prove scanout or card presentation.

## Risks / Trade-offs

- [Top rail is difficult to reach on glass] → preserve visible routes now and measure all-edge real-finger use before moving it.
- [History exposes secrets on shared glass] → hide sensitive preview bodies, bound records, and test unknown sender behavior; no lock-screen security is claimed.
- [System adapters report stale state] → display last confirmed value plus loading/stale/error status; never imply a command succeeded from tap alone.
- [Notification preview collides with app/keyboard] → suppress to history and count; replay is reachable without stealing focus.
- [Cards cannot meet measured Pixman cost] → retain metadata focus route and explicit unavailable wording; do not silently substitute a static thumbnail.

## Migration Plan

Land this planning change first. Implement shared tokens/route and state fixtures, then settings adapters, then the notification broker and surface. Integrate the visual card frame only after the existing card architecture/product gates. Package defaults in Nix. Ship behind a reversible shell configuration flag; failure returns to the current Apps/Windows/Keyboard/System session. Record host, installed-image, and physical-glass evidence separately before enabling by default. Stage 1, kernel, and device tree are unaffected.
